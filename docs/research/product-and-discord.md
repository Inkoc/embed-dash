# Product and Discord research

Research snapshot: 27 November 2026. The product is a self-hosted, single-operator-bot message composer with a live preview and multi-channel delivery. Later capabilities include history and editing, templates, scheduling, channel groups, imports, and richer channel types.

## Comparables and milestone 1

- [Discohook](https://github.com/discohook/discohook) designs and sends webhook messages, with rich editing, backups and bot-side features. Its webhook identity and per-webhook destinations differ from a single operator-owned bot spanning guilds; its current deployment also has several services, rather than a single-container target.
- [Discord Embed Editor](https://github.com/02Sila/discord-embed-editor) is an MIT-licensed static, self-hostable visual editor with drag-and-drop, validation and JSON/code export. Its documented workflow is exporting, rather than selecting bot channels and delivering messages.
- [Carl-bot](https://github.com/botlabs-gg/carlbot-docs/blob/master/docs/embeds.md) combines a dashboard preview and JSON editor with bot commands for sending and editing its own embeds. It is a hosted multipurpose bot, not an operator-owned self-hosted instance.
- [FiveUnity](https://www.fiveunity.com/documentation/content/embeds) supports bot or webhook delivery, saved messages, history, imports and editing; it also has a separate Components V2 editor. Its hosted dashboard and wider product are different from a small self-hosted deployment.
- The older [Discohook site](https://github.com/discohook/site) has a container image and webhook editor, but is deprecated in favor of the rewrite; it is not evidence of a maintained bot-based multi-guild workflow.

**Core actions defining milestone 1:**

1. Compose and change message content and embed elements, including fields, color and media URLs.
2. See a live, recognizable Discord-style preview while editing.
3. Detect invalid or over-limit input before sending, with actionable feedback.
4. Choose a destination accessible to the configured bot and send the message.
5. See whether delivery succeeded or failed and understand the failure.

These are the baseline tasks for this product, not a claim that an export-only editor itself sends messages. Multi-select, history, attachments, scheduling and the other planned capabilities are distinct from this baseline.

## Discord message contract and preview

[Message resource](https://docs.discord.com/developers/resources/message): content is at most 2,000 characters; a message can contain up to 10 rich embeds. Per embed: title 256, description 4,096, 25 fields, field name 256, field value 1,024, footer text 2,048, author name 256. The sum of those text properties across **all** embeds is at most 6,000; leading and trailing whitespace is trimmed for these limits. Duplicate embed URLs display only the first embed. An embed timestamp is ISO 8601; color is an integer RGB value (0–0xFFFFFF), shown as a side bar. Title and author URLs support HTTP(S); image, thumbnail and author/footer icon URLs support HTTP(S) and attachment references. For an upload use `attachment://filename` matching the multipart attachment filename; Discord documents supported image formats and filename restrictions in [Uploading Files](https://docs.discord.com/developers/reference#uploading-files). Server-generated `proxy_url`, dimensions, provider and video cannot be set on create.

File limits are separate from embed limits: Discord documents a default per-file limit of 10 MiB, potentially higher depending on context; the create-message request itself has a maximum size of 25 MiB. Do not assume a boosted guild or user upload allowance applies to a bot; handle Discord's rejection. See [Uploading Files](https://docs.discord.com/developers/reference#uploading-files) and [Create Message](https://docs.discord.com/developers/resources/message#create-message). Bound both individual files and the aggregate multipart request locally.

For classic message components, use up to five action rows, each with up to five buttons; a link button has style 5, a URL of at most 512 characters and no `custom_id`, and produces no interaction. A label is at most 80 characters. Components V2 has different composition rules and cannot be mixed with traditional content/embeds when its flag is set. See [component reference](https://docs.discord.com/developers/components/reference) and [message flags](https://docs.discord.com/developers/resources/message). `SUPPRESS_NOTIFICATIONS` (`1 << 12`) suppresses push and desktop notifications but can still produce a badge; `SUPPRESS_EMBEDS` hides embeds. Set `allowed_mentions: {"parse": []}` on create **and edit** to suppress user, role and everyone notifications; explicit allowlists require deliberate opt-in, permissions and actual mention text. [Allowed mentions](https://docs.discord.com/developers/resources/message#allowed-mentions-object) governs notifications, not whether text visually resembles a mention.

### Rendering fidelity and evidence limits

Discord's [formatting reference](https://docs.discord.com/developers/reference#message-formatting) defines user `<@id>`, role `<@&id>`, channel `<#id>`, custom emoji and Unix-second timestamps such as `<t:1700000000:R>` (relative, localized to the viewer). Its [Markdown guide](https://support.discord.com/hc/en-us/articles/210298617-Markdown-Text-101-Chat-Formatting-Bold-Italic-Underline) describes bold, italic, underline, strike, inline/fenced code, quotes, masked links, headings, lists, subtext and spoilers for messages. It does **not** specify an exhaustive syntax-by-embed-field matrix. [Carl-bot's documentation](https://github.com/botlabs-gg/carlbot-docs/blob/master/docs/embeds.md) notes limited formatting and unreliable mentions/masked links in titles, author and footer. Treat description and field values as the main rich-text surfaces, field names as a separate rendering case, and title, author and footer as restricted/plain-looking surfaces; do not promise that every message syntax (particularly headings, lists, subtext, spoilers, code blocks, mentions and timestamps) works in each surface without client tests. A masked link is `[label](https://example.com)`; title/author have their own URL properties. Mention names and colors depend on guild context and visibility, so unresolved IDs need a fallback. Never turn preview rendering into executable HTML.

Typical client layout places the colored bar on the left, the thumbnail at upper right and the main image below text, preserving image aspect ratio within client constraints; consecutive inline fields commonly fit three per row, often two beside a thumbnail. Discord does not specify fixed preview pixel sizes or a stable wrapping algorithm in the API contract: viewport, client and content can change layout. Validate thumbnail interaction, image scaling, and every Markdown/field combination against current desktop and mobile clients; do not claim pixel-perfect behavior from these heuristics.

## REST and permissions

- `GET /users/@me` identifies the bot; paginate `GET /users/@me/guilds` (up to 200 per page, using `after`) and `GET /guilds/{guild.id}/channels` to populate guilds and channels. Guild channels excludes threads; use the appropriate active/archived thread endpoints if threads become selectable. REST listing and fetching the bot's own member do not require a privileged Gateway intent; intents select Gateway events, and this design opens no Gateway connection. See [user](https://docs.discord.com/developers/resources/user), [guild](https://docs.discord.com/developers/resources/guild), and [Gateway intents](https://docs.discord.com/developers/events/gateway#gateway-intents).
- For a pre-check fetch guild, roles and `GET /guilds/{guild.id}/members/{bot.id}`, plus channel overwrites. Follow the documented [permission algorithm](https://docs.discord.com/developers/topics/permissions): owner/administrator bypass, base `@everyone` plus member roles, then everyone overwrite, combined role denies/allows, then member overwrite; account for implicit permissions and thread inheritance. Check `VIEW_CHANNEL`, `SEND_MESSAGES` (or `SEND_MESSAGES_IN_THREADS`), `EMBED_LINKS`, and `ATTACH_FILES` as applicable. A pre-check is advisory: permissions can change before the request, and Discord remains authoritative.
- `POST /channels/{channel.id}/messages`, `PATCH /channels/{channel.id}/messages/{message.id}` and `DELETE` on that message handle delivery and the bot's own copies. Use multipart `files[n]` plus `payload_json`; on edit explicitly retain existing attachment IDs in `attachments` alongside new files or they are removed. Persist a separate channel/message ID and result for each copy; partial edits and retries must be visible. [Message endpoints](https://docs.discord.com/developers/resources/message).
- Forum/media posts use `POST /channels/{channel.id}/threads` with a starter message; ordinary message creation is not the forum-post endpoint. Announcement publishing uses `POST /channels/{channel.id}/messages/{message.id}/crosspost`, subject to its channel and permission rules. See [threads](https://docs.discord.com/developers/resources/channel#start-thread-in-forum-or-media-channel) and [crosspost](https://docs.discord.com/developers/resources/message#crosspost-message).
- Respect dynamic per-route bucket headers and major-resource partitioning, and coordinate shared buckets across requests. On 429 use `Retry-After`/`retry_after` and global/scope information; do not hard-code route quotas. The global bot limit is 50 requests/second. The IP-based invalid-request threshold is 10,000 in 10 minutes for 401, 403 and 429, excluding shared-scope 429s; stop on invalid credentials and avoid repeating forbidden requests. [Rate limits](https://docs.discord.com/developers/topics/rate-limits).
- [`@discordjs/rest`](https://github.com/discordjs/discord.js/tree/main/packages/rest) with [`discord-api-types`](https://github.com/discordjs/discord-api-types) supplies a REST-only client, types and rate-limit handling without a gateway; raw fetch is viable only with careful bucket coordination and 429 handling.

## Security and deployment

Keep the bot token exclusively on the server, out of browser responses, logs, import/export, URLs and client bundles. Support a Docker Compose mounted [secret](https://docs.docker.com/compose/how-tos/use-secrets/) via an application-defined `BOT_TOKEN_FILE` convention; environment variables are a fallback, not encryption. Restrict secret and database file access and document token rotation. One instance token grants the instance's operators its permissions across all joined guilds.

Use server-side sessions with random identifiers and `HttpOnly`, `SameSite` cookies, `Secure` under HTTPS, expiration and rotation on login; enforce CSRF tokens and origin checks for state-changing requests, including login. Hash passwords with [Argon2id](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) using a unique salt and calibrated cost; rate-limit authentication. OAuth authorization-code flow requires state validation and a fixed registered redirect URI; request only `identify`, fetch `/users/@me`, compare the immutable user ID with the allowlist, then discard the access and refresh tokens. `identify` grants basic identity, not posting or account management permissions; a malicious operator can still capture the returned identity token while it is valid, so minimize its lifetime and exposure. See [OAuth scopes](https://docs.discord.com/developers/topics/oauth2#shared-resources-oauth2-scopes) and [user endpoint](https://docs.discord.com/developers/resources/user#get-current-user).

No-auth mode allows anyone who can reach the service to operate the bot. Bind the **host-published** Docker port to `127.0.0.1` (and IPv6 loopback only if intentionally configured), show a persistent warning, and do not expose it through a reverse proxy or remote tunnel. Container-internal binding alone does not make a published port local. For remote use require authentication and HTTPS.

Prefer passing user-provided media URLs through to Discord rather than server-side fetching. If fetching is necessary, defend against [SSRF](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html): restrict schemes, resolve and block loopback/private/link-local/metadata addresses, pin validated destinations, revalidate redirects and limit time, bytes and redirects. Treat uploads as untrusted, enforce body and file limits before buffering, use generated storage names and avoid serving active content from the app origin.

## Licensing and branding

Discord's [Developer Terms](https://support-dev.discord.com/hc/en-us/articles/8562894815383-Discord-Developer-Terms-of-Service), [Developer Policy](https://support-dev.discord.com/hc/en-us/articles/8563934450327-Discord-Developer-Policy) and [brand guidelines](https://discord.com/branding) govern API use, data and marks; avoid implied endorsement and do not bundle Discord logos. A visually useful preview is not blanket permission to copy proprietary assets or trade dress. Discord says [gg sans is not open source or available for external projects](https://support.discord.com/hc/en-us/articles/9507780972951-gg-sans-Font-Update-FAQ). Use an independently licensed approximation such as [Inter](https://github.com/rsms/inter) or [Noto Sans](https://github.com/notofonts/latin-greek-cyrillic), both OFL; [Lucide](https://github.com/lucide-icons/lucide) icons are ISC. Include the applicable license and copyright notices with bundled assets; bundle no other media.

Discord API JSON field names describe an interoperability contract, not a license to copy another application's implementation, sample content or assets. “Common community format” is ambiguous: identify a specific schema/version and its license before copying a schema or fixtures; Discohook's current repository is [AGPL-3.0](https://github.com/discohook/discohook), so avoid copying its code or assets without evaluating obligations. Independently implement documented compatibility and retain attribution where required.

## Blocking questions

- Which exact community JSON format and version must import/export support, and what compatibility behavior is required for unsupported fields? This blocks that feature's specification, not the initial composer.
- What measured client/version and tolerance define an acceptable “accurate” preview? Discord does not publish the exhaustive Markdown and layout contract needed to guarantee exact parity; establish a fixture matrix and acceptance threshold before promising it.
